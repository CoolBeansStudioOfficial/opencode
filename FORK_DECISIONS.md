# Fork decisions log

Judgment calls made while building the fork without the owner present. Each entry says what was chosen, why, and how to undo it.

## 2026-10-22

- **Permission modes live in session metadata** (`permissionMode`), enforced by `packages/core/src/plugin/permission-mode.ts`. "Ask permissions" defers to your config, which currently allows `edit` and `bash` globally, so it won't prompt for those until you remove them from `~/.config/opencode/opencode.json`.
- **Plan mode reuses OpenCode's Plan agent.** It takes effect from the next message, not mid-turn, so a running turn is not reconfigured.
- **Sidebar pins and groups are stored per device** (browser storage), not on the server. Phone and desktop keep separate pins. Moving them server-side would need a new store; deferred.
- **The sidebar follows the server selected on Home.** With several servers configured, switch servers from Home.
- **Claude theme is the default only when no theme was chosen before.** Existing installs keep their stored theme; pick "Claude" in Settings → Appearance.
- **The tab bar is hidden by default** via a new "Hidden" tab layout. Tabs still exist internally (the sidebar opens sessions as tabs); choose Horizontal or Vertical in Settings → General to bring them back. Mobile keeps its tab drawer.
- **No custom fonts in the Claude theme.** Claude's typefaces are proprietary; the theme changes colors only and keeps Inter.
- **The task list sits above the composer**, not under the latest message, so it stays visible while the transcript scrolls. It shows only while a task is pending or in progress.
- **The `todowrite` tool is on by default** (upstream hides it behind `experimental.todo`); set `"experimental": { "todo": false }` to turn it off.
- **No end-to-end model tests yet.** Your homelab llama.cpp (port 8099) was down, and TabbyAPI (port 5000) needs `TABBY_API_KEY`, which isn't set on this PC. Features were tested with unit tests, the server API and the browser instead.
- **57 core tests fail on this Windows PC before and after the fork changes** (shell, ripgrep/search, symlink and location tests: 5,589 pass). They fail identically with the fork's permission plugin disabled, so they are environment issues (Windows shell, symlinks), not regressions. Run them under WSL or CI to compare.
- **Remote access uses `tailscale serve`, not a public bind.** The server stays on `127.0.0.1`; Tailscale gives it an HTTPS tailnet address, which browsers need for installing the PWA and for push. I did not run `tailscale serve` (that changes your Tailscale config); steps are in `REMOTE_ACCESS.md`.
- **Web push lives in a core plugin** (`packages/core/src/plugin/web-push.ts`) with the `web-push` library, reachable through plugin RPC (`opencode.push`) so no HTTP API or generated client changes were needed. VAPID keys and subscriptions are stored server-side in plugin storage.
- **Push fires for**: root sessions finishing or failing, any permission request, and agent questions. The service worker skips the notification when the app is open and focused on that device, and the in-app notifier skips when push is on, to avoid doubles.
- **The push switch is per server** (Settings → server → Preferences) and only in the browser/PWA build; the desktop app keeps native notifications.
- **Push was tested with a local fake push service**, not a real phone: the browser pane here can't register service workers. Encryption, VAPID signing and the permission trigger were verified end to end.
- **Fixed a Windows bug in local builds**: the dev server indexed built web files with `\` paths, so the served web UI couldn't load its scripts.
- **Subagent sessions nest under their parent in the sidebar** (expand with the chevron; the active subagent's parent expands automatically). A running subagent accepts steering messages from its own view; an idle one stays read-only, because a new prompt there would start work whose result never reaches the parent.
- **New sessions in Git projects default to their own worktree** (Settings → Worktrees → default destination "New"), like Claude desktop. Upstream defaulted to the last used choice. The new-session screen still lets you pick Local or an existing worktree per session.
- **Artifacts are files.** The new `artifact` tool shows a file the agent wrote in the side panel (HTML, Markdown with Mermaid, `.slides.md` decks, SVG, CSV, PDF, images), and it re-renders as the agent edits. HTML runs sandboxed with no network, so artifacts must be self-contained; React-from-CDN artifacts are not supported. There is no visual design canvas yet.
- **The browser pane stays desktop-only** (it's an Electron view). On the web/phone build the agent's browser tools report that the browser is unavailable.
- **Git actions live behind a Git button in the session header**: commit all changes, push (sets upstream on first push), create a pull request and see its CI checks, using `git` and the GitHub CLI on the server. Pull requests always target the `origin` repository (your fork here), never `upstream`. Plugin RPCs run in the server's own location, so each Git call names its session directory explicitly. CI status refreshes when you open the dialog or press Refresh; there is no background CI watcher or auto-fix yet.
- **Not tested against GitHub**: commit, status and push errors were tested on a throwaway local repo; creating a real pull request was not, to avoid opening one on your account.
- **Memory lives in `~/.config/opencode/memory/`** (one Markdown file per memory plus a `MEMORY.md` index), shared by all projects. The index is added to every session's context, and the agent may read and write that folder without prompts (read-only subagents can only read it). There is no memory UI; open the folder to review or edit memories.
- **Scheduled tasks run on the server**: a task starts a new session in its folder and sends its prompt, on an interval or at a time of day (optionally only on certain weekdays, in the PC's local time). Manage them in Settings → server → Scheduled tasks, or ask the agent (it has a `schedule` tool). Tasks only run while the server is running; a missed slot runs once on the next check rather than catching up every missed run.
- **Testing touched your real OpenCode data**: the dev server uses the same data folder as OpenCode on this PC, so my test sessions (in throwaway folders under `%TEMP%\claude`) show up there. I deleted the test scheduled tasks; the leftover test sessions are listed in the final summary.
- **Claude Design = real web code on a canvas.** A `design.json` lists frames; each frame is a page of the project (`file`) or a route of the running app (`url`). There are no mockups and no handoff step: comments go to the agent, which edits the same source, and every frame reloads. Any existing HTML page can switch to the canvas with its "Design" button (desktop and mobile frames).
- **Design frames are served by the OpenCode server under `/design/<ticket>/...`.** Iframes can't carry the app's credentials, so a ticket in the URL path (issued over authenticated RPC, valid 24 hours, bound to one folder or one loopback port, kept in memory) grants access. File frames can't escape their folder. Live frames proxy only `127.0.0.1:<port>`, with the inspector injected and frame-blocking headers removed. A frame's root-relative requests (`/src/main.tsx`) are redirected back under its prefix by referer, which is how Vite-style module graphs load through the proxy.
- **Live frames get their own origin on this machine.** Tested on the Bazoodle site (`game-platform/site`): its router reads `location.pathname`, so under the sub-path proxy every route showed "can't find that page". The server now starts a loopback-only proxy per dev-server port (same paths, inspector injected, WebSockets passed through for the dev server's own hot reload) and the canvas uses it when the app is opened on the server machine. Remote clients (phone over Tailscale) still use the sub-path proxy, which works for apps that don't route on the path.
- **The design watcher watches top-level subfolders separately.** Bun ignores `recursive` when the process already watches the same folder non-recursively (the server watches project roots), so on a real repo no nested change was seen. Each top-level folder (except `node_modules`, `.git`, build output) now has its own recursive watch.
- **Live frames reload on file changes, not hot module replacement.** The dev server's HMR websocket isn't proxied. A recursive watch on the project folder (ignoring `node_modules`, `.git`, `dist`, `build`) reloads every frame about a second after any change. Linux lacks recursive `fs.watch`, so there frames reload only when reopened.
- **The design system is the project's own stylesheet**: the manifest's `system` points at a real CSS file, and its custom properties show in the canvas "System" panel. Nothing is copied.
- **Export**: each frame has an "Open" link to the real page (save or print it to PDF from the browser). There's no PNG export yet.
- **Symlinked repo files are real copies on this PC** (Windows without Developer Mode). They are marked `skip-worktree`, so Git ignores local changes to them.
